# 手环导航页减负与受控 GC（W-706）

本文件记录 `band-app/src/pages/index/index.ux` 的低风险减负改动、可读性能线索，以及
**仍未验证**的部分。改动只碰四个文件：`band-app/src/pages/index/index.ux`、
`band-app/test/startup.test.js`、`band-app/src/manifest.json`（仅 versionCode 9→10）与本文档。
通信协议、ack、15 秒无帧、提醒震动、显示规则、图标资源、`band-app/src/common/`、
`scripts/`、手机端 `app/`、`design/` 一律未动。

**本文件不宣称真机流畅、不宣称已确认根因、不把主机测试当作实机通过。**

---

## 1. 用户反馈

导航界面停留久了，操作明显卡顿（手环端页面在长时间导航中响应变慢）。

## 2. 可能原因（只有已有依据，不是已确认根因）

只列已有来源能支撑的假说与代码事实。**这些都不是经实机测量确认的根因**：

1. **每次重绘都在重写全部页面数据。** 页面每秒一次 tick，基线的 `applyDisplay` /
   `applyAbnormal` 无条件给每个数据字段赋值。在 Vela 里 `data` 字段写入会走
   observer/数据代理，没有变化也照样赋值就是白白触发重绘与内存开销。
   来源：官方「内存优化」——*和 UI 无关、不需要绑定的数据不要声明到 viewModel 里*、
   *页面对象更新时尽量原地更新*。
2. **每帧重复解析同一个 JSON 字符串。** 基线的成功字符串帧在 app.ux、session、
   reducer 各解析一遍（见第 4 节实测 3 次），每秒都在做重复解析。
3. **提醒历史数组无上界，且每次携带都整份拷贝。** 基线 `carryPrev` 对
   `remindedTurn` / `remindedAdvisory` 每次都 `.slice()`，数组本身没有长度上限。
   来源：官方「内存优化」——控制三方应用内存占用是手表验收要求。
4. **图标位图被运行期放大。** 基线 CSS 的 `.nav-icon` 显示盒已是 140×140，但随包
   PNG 是 112×112，宿主必须把位图放大到 140 才显示。来源：官方「常用业务优化 ·
   设备帧率的优化建议」——*图片大小与 div 或 image 组件大小保持一致，尽量不缩放图片*。

## 3. 每项改动对应的官方建议

两份可核实的官方建议（本次实际抓取确认可达，标题即页面标题）：

| 编号 | 标题 | URL |
| --- | --- | --- |
| S1 | 内存优化（Xiaomi Vela JS 应用 / 最佳实践） | <https://iot.mi.com/vela/quickapp/zh/guide/best-practice/memory.html> |
| S2 | 常用业务优化（Xiaomi Vela JS 应用 / 最佳实践，含「设备帧率的优化建议」） | <https://iot.mi.com/vela/quickapp/zh/guide/best-practice/business.html> |

| 改动 | 对应建议 | 依据原文（要点） |
| --- | --- | --- |
| 页面数据字段逐字段去重（`setIfChanged`） | S1 | *和 UI 无关，不需要绑定的数据，不要声明到 viewModel 的数据里，减少 observer 或者数据代理*；*页面对象更新时，尽量原地更新，不要重新赋值* |
| 标题→动作 id 反查表改为模块加载时建一次 | S1 | 同上：不要每次重绘重建临时对象 / 减少数据代理开销 |
| 受控 `global.runGC()`（≥30 秒后首次、之后 ≥60 秒一次、`try` 包住） | S1 | *调用 runGC 方法……及时进行垃圾回收，避免内存泄漏。不要频繁调用，防止页面卡顿* |
| 提醒历史各限 32、重复帧不再整份拷贝（W-704，本单复核） | S1 | 控制三方应用内存占用，符合手表验收标准 |
| 图标随包即为 140×140，运行期不再放大（W-705，本单复核） | S2 | *图片大小与 div 或者 image 组件大小保持一致，尽量不缩放图片* |
| 每帧只解析一次 JSON（W-704，本单复核） | S1 | 减少每帧重复工作，降低页面卡顿风险 |
| 诊断性能行只在展开时写、且去重 | S1 | 不需要绑定的数据不放进 viewModel；诊断块仍默认收起，主页面无新增常驻文字 |

## 4. 前后对照

对照在同一固定状态、同一可计数宿主下测量：一个真实 `session`（`action=left`、
`distanceM=300`、`roadName=中山路`，已收到帧且未超时），页面数据字段全部以可计数 setter
装配，按 1 Hz 连续两次 tick 计数。基线取 git 提交
`0c53e7c3594b0812b899f582333856e5b41eae02`，**不修改基线**，只在内存中加载其源码计数。

**测量方式（可复现）**：基线侧用 `git show 0c53e7c:band-app/src/...` 读出源码，在一次性
Node 脚本里以内存 CommonJS 加载器 + 同一套可计数 setter 宿主计数；工作树侧用同样的宿主
装载当前文件。计数脚本是一次性测量工具，未提交进仓库；提交进仓库的是
`band-app/test/startup.test.js` 里新增的 setter 计数用例（它断言的是「稳定态 tick 除
`lifeTick`/`lifeText` 外零写入」这一形状）。

### 4.1 页面数据写入次数（每秒 = 每次 tick）

生命周期字段与非生命周期字段**分开说**：

| 项目 | 基线 0c53e7c | 本次（W-706） |
| --- | --- | --- |
| 稳定态正常 tick：数据写入总数 | **17** | **2** |
| ↳ 其中非生命周期字段（15 个显示/诊断字段） | **15** | **0** |
| ↳ 其中 `lifeTick` + `lifeText` | 2（各 1） | 2（各 1） |
| 稳定态正常 tick：重写的非生命周期字段 | 15 个全部 | 无 |
| 连续两次 tick 后显示内容 | 左转 / 300米 | 左转 / 300米（不变） |

异常路径（`applyAbnormal`，`$app.$def` 缺失）：

| 项目 | 基线 0c53e7c | 本次（W-706） |
| --- | --- | --- |
| 第 1 次调用写入 | 15 | 15 |
| 第 2 次（重复、值未变）调用写入 | **15** | **0** |

即：显示内容没变的连续 tick，除既有的 `lifeTick` / `lifeText` 外**零数据写入**；
基线是每秒 17 次写入，本次稳定态每秒 2 次（且这 2 次就是必须计数的生命周期字段）。

### 4.2 每帧 JSON.parse 次数（app.ux 成功字符串帧路径）

计数方式：把 `JSON.parse` 换成计数器，向真实 `app.ux` 的 `onmessage` 喂一条
`{ data: "<JSON 字符串>" }`，读计数。

| | 基线 0c53e7c | 本次 |
| --- | --- | --- |
| 成功字符串帧每帧 `JSON.parse` 次数 | **3** | **1** |
| 帧结果（title） | 左转 | 左转（不变） |

### 4.3 提醒数组上限与重复帧拷贝

| 项目 | 基线 0c53e7c | 本次 |
| --- | --- | --- |
| `remindedTurn` / `remindedAdvisory` 上限 | **无上界** | **各 32** |

### 4.5 入帧环与 GC 统计口径

- **入帧环**：`band-app/src/common/session.js` 里一个固定容量 **600** 的时间戳环，
  记录每个已处理帧的接收时刻（含心跳与不可解析帧）。`inboundStats(nowMs)` 返回
  `{count, retained}`：`retained` 是环内现存的项数（`<=600`），`count` 是其中落在
  **最近 60000 ms 窗口**内（`ts <= now && now - ts < 60000`）的项数。它**不参与**
  `reduceDisplay`，不改变任何显示逻辑。
- **GC 统计口径（`gcCallCount`）**：记录的是**实际发起调用的尝试次数**——只有
  `typeof global !== "undefined"` 且 `typeof global.runGC === "function"` 时才自增并调用；
  `runGC` 抛错计入该次尝试（异常被 `try` 吞掉，不影响显示）。缺 `global` 或没有
  `runGC` 时计 0，且不会每 tick 重试。
- **耗时口径**：`gcLastMs` 与 `perfMaxTickMs` 均为非负**整毫秒**；`perfMaxTickMs` 是
  「本分钟桶内 tick 最长耗时」，用 `Date.now()` 在 tick 前后取差（含 GC）；分钟桶以
  `onInit` 时刻为锚，每 60 秒重置一次。

### 4.6 诊断性能行（仅展开可见）

`data` 只新增一个响应式字段 `perfText`（初值空串），仅在 `debugVisible === true` 的
tick 里组装并去重写入，显示在既有 `diag` 块新增的一行「性能 …」，格式：

```
性能 最长<本分钟tick最长ms>ms 入帧<最近一分钟入帧数>帧 GC<调用次数>次 <最近一次耗时>ms
```

调用次数、最近一次耗时、本分钟最长耗时都是**普通实例属性**（`gcCallCount`、`gcLastMs`、
`perfMaxTickMs` 等），不放进 `data`、不参与渲染。诊断块仍默认收起，主页面没有新增任何
常驻文字，也没有新增 `console` 日志。

## 5. 仍未验证什么

- **真机卡顿是否因此消除：未验证。** 没有任何实机操作、长时间导航或帧率测量。
- **`runGC` 在真机上的耗时：未验证。** 主机侧只有合成假时钟；真机 GC 停顿未知。
- **性能行的数值：未验证。** 第 4.6 节的数字来自有界 Node 主机，不是真机读数。
- **正负 3% 的 alpha 容差之外的观感：未验证。** 只有静态 PNG 比值，没有真机目视。
- 本单所有测试都是**合成夹具 / 有界主机**：手环 VM 是有界 Node 运行时，不是官方
  QEMU 固件；测试不是实机证据，也不代表高德真实通知的中文解析已验收。
- 未验证在高帧率/高负载下的实际每秒数据写入是否仍为 2 次（主机按 1 Hz 计时）。
