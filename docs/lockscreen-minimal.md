## 2. 各开关与字段怎么读

### 2.1 主页的桥开关与模式

- **「开启导航桥」/「关闭导航桥」**：这是唯一的用户开关。桥关闭时，收到的任何高德包通知
  都会被记为 `AMAP_NOTIFICATION_IGNORED`（detail `bridge-off`）并**丢弃，不解析、不发送**。
  桥开启且前台会话在跑时，新的可解析指令走 UPDATE 更新通道。
- **步行 / 骑行**：模式由**用户在自研 App 内手动选择并记忆**（持久化在 `navigation` 偏好里），
  不会自动从高德推断。**默认模式为骑行**（`NavProtocol.DEFAULT_MODE`，界面分段控件骑行在左）；
  偏好里没有值或值无法识别时一律按骑行处理，只有用户显式选过步行才走步行。
  首版阈值按模式区分：步行 30 米临近提醒，骑行 100 米临近提醒；
  这里的模式只影响导航引擎的判定，不改变时间线的字段含义。

### 2.2 计数摘要一行

| 字段 | 含义 |
|---|---|
| 通知数 | 60 秒窗口内**四类高德通知事件**之和（见 2.4）。它计的是“收到并处理了一条高德包通知”，不代表高德产生了一条新指令 |
| 发送帧数 | 只计 `FRAME_SENT`：本地通道**接收了一次入队报文**（每帧带协议 id 后 6 位） |
| ACK 数 | 只计 `ACK_RECEIVED`：**手环回执** |
| RTT 最近 / 平均 | 该窗口内每条 ACK 的 `发送→回执` 往返毫秒的**最新值与平均值**；窗口内没有 ACK 时显示「无样本」，**不显示 0** |

**摘要的三个计数与 RTT 都是精确值，不是“至少这么多”。** 它们来自**分类时间戳环**
（通知 / 发送帧 / ACK 各存最近 1200 个 elapsed 毫秒戳），
与两个环的条目无关：即使流量密集到把环里的旧条目挤掉，窗口计数也不会被截断。

**窗口精确到毫秒。** 查询时刻 `now` 时，只有满足 `elapsed <= now` **且** `now - elapsed <= 60000`
的记录计入；**未来**（含与 `now` 同一毫秒之外、稍后一点写入的记录）与**超过 60 秒的过期**记录都不计，
恰好 60 000 毫秒整仍然计入。查询时刻是任意的：查询过去、查询未来、打乱顺序查询都不淘汰任何记录，
相差超过 60 秒的两条记录各自在自己的窗口里回答，互不覆盖。所以“刚好 60 秒前”的事件仍然计入，
不再有一秒粒度的边界误差。

**容量饱和：** 每类每分钟超过 1200 条（即持续每秒 20 条以上）时，该类的窗口时间戳环饱和，
最早的时间戳被丢弃，那一类的窗口计数可能少算；ACK 往返样本另有 600 条上限，超过后
「最近 / 平均」只反映仍然保留的样本。这是内存上限，不是正常运行时的限制：
每秒 10 帧持续 60 秒刚好 600 条，远未饱和。

**发送帧数 ≠ 轮次。** 心跳循环每转一圈记一条 `SEND_ROUND`（轮次），一轮里可能一帧都没发；
帧数只能来自 `FRAME_SENT`。**轮次也不等于发送成功。**

### 2.3 时间线一行的四个部分

| 部分 | 说明 |
|---|---|
| 墙钟时间 | `System.currentTimeMillis()`，本地时区 `HH:mm:ss`。可跨进程重启比较，但会被用户改时间/NTP 校正影响 |
| `+elapsed 毫秒` | `SystemClock.elapsedRealtime()`（开机以来的单调毫秒）。**不受改时间影响**，用于算"两条事件之间过了多久"；与墙钟不能互相换算 |
| 事件类别 | 固定枚举，见 2.4。是**类别词**，方便按类别分组，无需解析自由文本 |
| detail | 已脱敏：布尔、枚举词、毫秒，以及协议/SDK/ACK id 的**后 6 位**；超过 60 字符会被截断 |

### 2.4 事件类别怎么读

| 类别 | 什么时候记 | detail 里通常是什么 |
|---|---|---|
| `SCREEN_ON` / `SCREEN_OFF` / `SCREEN_UNLOCK` | 屏幕亮 / 灭 / 解锁广播 | 屏幕状态词 |
| `DEVICE_IDLE_CHANGED` | 系统 Doze 空闲模式变化 | `idle=0/1` |
| `POWER_SAVE_CHANGED` | 省电模式变化 | `save=0/1` |
| `LISTENER_CONNECTED` / `LISTENER_DISCONNECTED` | 通知监听**真的连上/断开**时 | `connected` / `disconnected` |
| `AMAP_NOTIFICATION_ACTIVE` | 解析出可识别的进行中指令 | 状态词 |
| `AMAP_NOTIFICATION_UNRECOGNIZED` | 高德包通知**无法识别方向/内容** | 状态词 |
| `AMAP_NOTIFICATION_ENDED` | 确认为导航结束 | 状态词 |
| `AMAP_NOTIFICATION_IGNORED` | 桥关闭，或高德包通知不是导航通知 | `bridge-off` / `not-navigation` |
| `SEND_ROUND` | 心跳循环转了一圈 | `idle=… interactive=… wakeLock=… node=…` 四个布尔 |
| `FRAME_SENT` | 本地通道接收了一帧 | `frame id=xxxxxx` |
| `SDK_TASK_SUCCEEDED` / `SDK_TASK_FAILED` | SDK `Task` 的成功/失败回调 | `ok=0/1 id=xxxxxx reason=<类别>` |
| `ACK_RECEIVED` | 收到手环回执 | `ref=xxxxxx rttMs=<毫秒>` |
| `RECOVERY_RESULT` | 一次后台恢复尝试的结果 | `ok` / `failed:<异常类名>` / `skipped` |

**两个环分开存放，互不挤占：** 八个系统生命周期类别（`SCREEN_*`、`DEVICE_IDLE_CHANGED`、
`POWER_SAVE_CHANGED`、`LISTENER_CONNECTED`/`DISCONNECTED`、`RECOVERY_RESULT`）进**状态环**
（容量 200）；九个传输类别（`SEND_ROUND`、`FRAME_SENT`、`SDK_TASK_*`、`ACK_RECEIVED`、
四类 `AMAP_NOTIFICATION_*`）进**流量环**（容量 120）。**再多流量也不会挤掉系统事件。**
合并列表（旧调用方的 `snapshot`）按 elapsed 新到旧整齐合并两环，同一毫秒保持新记录优先。

### 2.4.1 「最近一次」14 行怎么读

每行格式为 `类别：HH:mm:ss（N 秒前）累计 M 次`：

- **HH:mm:ss** 是该类**最近一条**事件的墙钟时间；
- **N 秒前** = `SystemClock.elapsedRealtime()` 减该条记录的 elapsed，再除 1000。
  **不用墙钟算差**（改时间、NTP 校正不会影响它）；
- **M 次**是该类事件**自本次进程启动以来的累计次数**。高德通知是一行：四类合并取最近一条，
  **累计次数为四类之和**；
- 该类从未发生过时整行显示「尚无」，不显示 0，也不推测时间。
- 最近时间与累计次数与环容量无关：流量把环挤满后，这两项仍然准确。

**「监听已连接」只代表系统真的把监听服务绑上了。** 只有通知权限被授予、但监听服务没绑定住时，
`LISTENER_CONNECTED` 不会出现——权限和"活着"是两件事。

### 2.5 后台策略区

- **`电池优化豁免：是 / 否`**：`isIgnoringBatteryOptimizations()` 的实时结果，来自系统 `PowerManager`。
  它是**系统状态**，不是"你按过按钮"。
- **两个按钮不等于授权已经生效。** 「允许后台运行」会先弹系统的直接豁免请求
  （`ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` + 本应用包 URI）；被系统拒绝
  （`ActivityNotFoundException` 或 `SecurityException`）时自动回退到电池优化设置页
  （`ACTION_IGNORE_BATTERY_OPTIMIZATION_SETTINGS`），需要用户在那里自己选。
  只有上面那行变成「是」，豁免才算生效。「打开小米运动健康应用信息」打开官方 App 的
  系统详情页，供用户自行检查它的后台策略——**本应用不修改官方 App 的设置，也不代替用户点选**。
- **最近一次后台恢复**：`lastRestoreText` 与它的墙钟时间。三种取值：
  - `ok` —— **只表示"启动前台服务的调用没有抛异常"**。它**不代表**手环收到了数据，
    不代表监听重绑成功，不代表锁屏下能持续发送。
  - `failed:<异常类名>` —— 启动调用抛了 `RuntimeException`，只记异常**类名**，不记堆栈、不记原文。
  - `skipped` —— 该次广播不满足恢复条件（桥被用户关掉了，或不是开机/覆盖安装这两类广播）。
  - 空 / 「尚无记录」—— 本次进程内还没发生过恢复尝试。

### 2.6 关于 SDK、回执和时间线本身

- **SDK `Task` 成功不等于手环收到。** `SDK_TASK_SUCCEEDED` 只是 SDK 层回调成功；
  真正的到手证明是 `ACK_RECEIVED`。两者在时间线上是**分开的类别**。
- **RTT** 是本地记录的"发送到回执"毫秒差，用的是单调时钟；它是**端到端观测**，
  不区分耗时花在 SDK、系统通道还是手环侧。
- **时间线在内存里，进程退出即丢**，没有持久化。两个环各自封顶（状态 200 / 流量 120）；
  如果 60 秒内某类事件超过它那个环的容量，**那个环里的旧条目会被挤掉**，分块列表（系统事件 40 条 /
  最近传输 20 条）只能展示仍然保留的那部分。但**计数摘要与「最近一次」不再受影响**：
  前者来自分类时间戳环（且只有严重超标时才会饱和，见 2.2），后者来自按类别索引的数组，都与环容量无关。
- 时间线里的数值**本身**还没有实机校准过（见第 4 节）。

### 2.7 唤醒锁何时持有

本小节由 mission `MiRing-Wakelock-Nav-Only-20261021` 引入，说明唤醒锁的持有规则**应当**是
“只在导航期间持有”。以下规则是设计约定，**不是实机验证结论**：本工作项没有运行 `adb`、
没有设备输出，也不宣称省电或息屏链路已通过（见第 4 节新增三行）。

**三条理由，任一成立即持有** `PARTIAL_WAKE_LOCK`（标签 `MiNavigateRing:probeHeartbeat`）：

1. **高德导航通知正在显示**；
2. **夹具最新内容为 `active`**；
3. **熄屏定时回归进行中**。

三条都不成立时：**理由消失后再持有 30 秒，然后释放**；30 秒是收尾缓冲，不是新的持有条件。
**其余时间不持有唤醒锁，CPU 可以休眠。**

**`SEND_ROUND` 里的 `wakeLock` 字段**（见 2.4）表示**本轮评估之后**锁是否持有：
`wakeLock=1` 说明这一圈评估完锁是持着的，**但不代表这一轮一定发出去了帧**；
**没有导航时出现 `wakeLock=0` 是预期行为，不是故障**，不要把它当成链路坏了的证据。

**待机副作用（预期现象，不是故障）：** 没有导航且屏幕熄灭、系统进入休眠时，心跳循环随 CPU 一起暂停，
`SEND_ROUND` / `FRAME_SENT` 会停下来。手环导航页以 `STALE_AFTER_MS`（`band-app/src/common/codec.js` 的
`15000` 毫秒）作为本机收帧活跃度超时：超过 15 秒收不到新帧，手环显示「通信连接中」并隐藏旧转向。
**开始导航后锁重新持有，链路恢复。**（本票**不改手环端**，这条只是说明现象与常量出处。）

**夹具测试做完要收尾：** 手工测试用夹具时，测完请发「空闲」或「结束导航」夹具，让三条理由都消失，
锁才会在 30 秒收尾后释放；只停在 `active` 夹具上，锁会一直被当作“导航中”而保持持有。

**给用户的核对命令（仅供参考，本票未运行）：**

`adb shell dumpsys power`

在输出里找 `probeHeartbeat`：锁持有时会有一行 `PARTIAL_WAKE_LOCK`；找不到这一行就表示当前没有持有。
这条命令本工作项**没有执行**，输出以用户自己实测为准。

## 3. 用户锁屏自测步骤（各一次）

前提：手机与手环已按既有方式绑定（**保留现有绑定**），高德已开始步行或骑行导航，
自研 App 里「开启导航桥」已打开、模式已选对。**不要求也不建议解绑、恢复出厂、
升级固件或修改手机系统安全设置。**

进入诊断页：主页底部「连接诊断与测试」。本节两次测试**各做一次**，各自记录"测试前"与
"测试后"的字段。

> 记录方式二选一：
> （a）**诊断页直接读**：测试前后各截一次「运行时间线」摘要、「最近一次」14 行与「后台策略诊断」两行；
> （b）**`adb logcat` 读日志 tag `MiRingTimeline`**，例如
> `adb logcat -s MiRingTimeline`（只过滤这一个 tag）。命令**仅供用户参考**。

### 3.1 测试一：手机放桌面静止 10 分钟（锁屏）

前提补充：**必须在高德导航进行中（或有 `active` 夹具）时测**——唤醒锁只在导航期间持有（见 2.7）；
**没有导航时 `wakeLock=0` 是预期，不是故障**，那种状态下测不到锁屏发送。

1. 进诊断页，记下**测试前**：
   - 计数摘要整行（通知 / 发送帧 / ACK / RTT 最近与平均）；
   - 「最近一次」各行的墙钟时间、N 秒前与累计次数（至少记 `屏幕灭`、`发送帧`、`ACK`、`恢复结果`）；
   - `电池优化豁免：是/否`；
   - `最近一次后台恢复：<词>（<时间>）`。
2. 回到高德保持导航进行，**锁屏，把手机放在桌面上静止 10 分钟**（不移动、不点亮）。
3. 10 分钟后解锁，回到诊断页（不用重进，诊断区每秒自刷新），记下**测试后**同样的几项，
   并翻看这 10 分钟内的「系统事件」与「最近传输」两块列表。
4. 重点看：
   - 熄屏后「最近一次」里 `发送帧` / `ACK` 是否**继续更新**（N 秒前应该很小），
     且它们的**累计次数比熄屏前更大**——累计与环容量无关，所以只要链路还在，M 就应该涨；
   - 最后一次 `发送轮次` 距熄屏（`屏幕灭` 行的墙钟时间）过了多久：用两行的 `N 秒前` 相减，
     或者用两个墙钟时间相减；熄屏后如果轮次不再记录，M 会停在熄屏之前；
   - `ACK` 行的 `N 秒前` 是否合理（不应是几十分钟），需要时在时间线里查 `ACK_RECEIVED` 的 `rttMs`；
   - 是否有 `SCREEN_OFF`、`DEVICE_IDLE_CHANGED`（`idle=1`）、`POWER_SAVE_CHANGED`；
   - 是否出现 `LISTENER_DISCONNECTED`（监听被系统断开）；
   - 「恢复结果」的累计次数与最近时间是否落在测试窗口内。

### 3.2 测试二：手机放口袋里步行 10 分钟（锁屏）

前提补充：**必须在高德导航进行中（或有 `active` 夹具）时测**——唤醒锁只在导航期间持有（见 2.7）；
**没有导航时 `wakeLock=0` 是预期，不是故障**，先开始导航再计时。

1. 同样先记**测试前**：计数摘要、「最近一次」各行（尤其 `发送轮次`、`发送帧`、`ACK`、`监听断开`）与后台策略两行。
2. 保持导航进行，**锁屏，把手机放进口袋步行 10 分钟**（不刻意点亮屏幕）。
3. 结束后记**测试后**同样的几项，并翻看这 10 分钟的「系统事件」与「最近传输」列表。
4. 重点看：与测试一同样的几类事件，外加
   - 口袋环境下是否有**监听被断开又重连**（`LISTENER_DISCONNECTED` 后是否出现
     `LISTENER_CONNECTED`）；
   - 高德真实通知的四类事件（`ACTIVE` / `UNRECOGNIZED` / `ENDED` / `IGNORED`）中出现了哪几类，
     `UNRECOGNIZED` 多不多——**不可识别的方向必须以 `UNRECOGNIZED` 显式出现，
     不允许被当成直行或猜测环岛出口**。

### 3.3 两次都要比对的四件事

1. **熄屏后链路还在不在**：用「最近一次」里 `发送帧` 与 `ACK` 两行的**累计次数**比对
   “测试前”与“测试后”——只要还在涨，链路就还在记录；不再涨或 N 秒前停在熄屏时刻，就要查时间线。
   同时对比“测试前 60 秒窗口”与“测试后 60 秒窗口”的计数摘要（两个窗口都是精确值）。
2. **豁免状态**：`电池优化豁免` 是否已经是「是」；如果不是，测试结果不能用来判断
   "锁屏链路不行"——先按第 2.5 节的说明把它变成「是」再测。
3. **恢复结果**：「恢复结果」行是 `ok` 还是 `failed:<类名>` 还是 `skipped`，
   以及它的墙钟时间与累计次数是否落在测试窗口内。
4. **监听连断**：这 10 分钟「监听断开」的累计次数有没有增加；增加的话后面有没有重新
   「监听连上」。

**注意：以上步骤是给用户的，本工作项（W-711）没有执行其中任何一条，也没有设备输出。**

## 4. 仍未验证什么（全部 `unverified`）

以下项目**没有取得任何实机证据**，本次交付**不宣称任何一项通过**：

| 未验证项 | 说明 |
|---|---|
| HyperOS 上「开机恢复」是否生效 | 开机广播 `ACTION_BOOT_COMPLETED` 在 HyperOS 上是否真的送达、恢复是否真的跑起来，未验证。可能还需要用户在系统里额外授予**「自启动」**权限；是否需要、授予后是否就够，都没有证据 |
| HyperOS 上「覆盖安装恢复」是否生效 | `ACTION_MY_PACKAGE_REPLACED` 路径同上，未验证 |
| `requestRebind` 是否让监听重绑 | 重绑是 best effort，被系统拒绝会被吞掉且**不记为恢复失败**；它到底有没有让监听重新连上，未验证 |
| 电池优化豁免是否让锁屏持续发送 | 豁免为「是」之后，锁屏/Doze 下 `FRAME_SENT`/`ACK_RECEIVED` 是否持续，未验证。豁免只是**必要条件候选**，不是已证实的充分条件 |
| 时间线数值本身 | 摘要里的通知/帧/ACK 计数与 RTT 数值都还没在实机上校准过；双环容量与分类时间戳环只在宿主 JVM 测试里推演过，没有实机数据 |
| 「允许后台运行」按钮的实机行为 | 直接请求被拒时的回退是否真能打开设置页、用户操作后 `电池优化豁免` 是否真的变「是」，未验证 |
| 手环端渲染与震动 | 不在本次闭环范围内；本文件不涉及，也不据此宣称手环侧任何行为 |
| 没有导航时 CPU 休眠、心跳暂停后手环页面的实际表现 | mission `MiRing-Wakelock-Nav-Only-20261021`：未持有唤醒锁时 CPU 休眠、心跳随之中断，手环导航页是否真的在 15 秒后显示「通信连接中」、旧转向是否真的被隐藏，**均无实机证据**。`STALE_AFTER_MS` 只是代码常量，不是实测结论。状态 `unverified` |
| 导航开始时 CPU 正在休眠的首帧延迟 | 手机在无导航的休眠状态下开始导航时，从锁重新持有到第一帧真正到达手环的延迟有多长（是否超过手环 15 秒活跃度窗口、用户多久才看到画面），**未验证**。状态 `unverified` |
| 唤醒锁只在导航期间持有后的实际省电量与导航中息屏链路稳定性 | “只在导航期间持有”是否真的带来可测的待机省电，以及改为该策略后导航中息屏链路的稳定性（是否出现发送中断、卡顿、ACK 缺失），**未验证**；本文件不宣称已省电，也不宣称息屏链路稳定。状态 `unverified` |

另外，本工作项**没有采集任何真实高德通知**：任何合成夹具都不构成"中文真实解析已验收"；
也**不伪造通知样本或实机结果**。
